1. What you get, in one paragraph

Every user of this JupyterHub automatically gets their own private Cloud Storage bucket, mounted in the notebook at ~/gcs. It is created for you the first time you log in — there is no ticket to file, no key to download, and no gcloud auth login to run. Nobody else can read it, including other users of the same hub. Put your datasets, model weights and checkpoints there. It is effectively unlimited, and it survives everything: pod restarts, node replacement, even a cluster rebuild.

2. The three places you can put files — and how to choose

LocationWhat it really isSizePrivate?Use it for
~ (/home/jovyan) A 20 GB SSD persistent disk (premium-rwo), attached to your pod 20 GB, fixed Yours Notebooks, code, git checkouts, requirements.txt, conda envs
~/gcs Your own private GCS bucket, FUSE-mounted Effectively unlimited Yes — only you Datasets, model weights, checkpoints, results, anything large
~/shared A team GCS bucket, mounted read-only Effectively unlimited Readable by all hub users Common datasets someone already downloaded once

The single most important rule: large data goes in ~/gcs, not in ~. Your home disk is 20 GB and filling it will wedge your notebook — JupyterLab stops being able to save, sometimes without a clear error.

Your bucket name follows your username: gs://hdlab-elideng-jupyter-<your-username>. For example elideng@google.com gets gs://hdlab-elideng-jupyter-elideng. Most of the time you never need to type it, because ~/gcs already points at it.

When you do need the name — for gcloud storage commands, or a gs:// URL in Python — do not guess it and do not try to list it. Read it off your own mount:

findmnt -n -o SOURCE ~/gcs        # -> hdlab-elideng-jupyter-elideng

Save it in a variable so the commands later in this guide can be pasted as-is:

export MY_BUCKET=$(findmnt -n -o SOURCE ~/gcs)

That works with no permissions at all, and it stays right even if your username had to be adjusted to be a legal bucket name. Put the export in ~/.bashrc and every gs://$MY_BUCKET/... in this guide will just work.

What will not work is a bare gcloud storage ls — that asks "what buckets exist in this project?", which you are deliberately not allowed to ask. See §7; it is the isolation doing its job, not a broken setup.

You will be offered three. Every one of them gets ~/gcs and ~/shared — the workspace is not a GPU feature.

Step 3 — Open a terminal and confirm your workspace is really there

In JupyterLab: File → New → Terminal. Then:

ls -la ~/gcs
gcloud auth list
findmnt -n -o SOURCE ~/gcs

What you should see, and what each line proves:

$ id
uid=1000(jovyan) gid=100(users) groups=100(users)

$ ls -ld ~/gcs
drwxrwxr-x 1 1000 100 0 Aug 27 06:45 /home/jovyan/gcs      # owned by you, writable

$ gcloud auth list
                     Credentialed Accounts
ACTIVE  ACCOUNT
*       hdlab-elideng.svc.id.goog                          # your pod's own identity

$ findmnt -n -o SOURCE ~/gcs
hdlab-elideng-jupyter-elideng                              # your bucket's name

That hdlab-elideng.svc.id.goog account is expected and correct — it is not a sign that something went wrong. Your pod authenticates as itself using Workload Identity, not as you personally. That is why there are no keys anywhere in this setup, and nothing for you to gcloud auth login into.

Now save the bucket name so the rest of this guide can be copy-pasted:

export MY_BUCKET=$(findmnt -n -o SOURCE ~/gcs)

Add that same line to the end of ~/.bashrc so every new terminal already knows it. Now this works:

gcloud storage ls "gs://$MY_BUCKET/"     # works: it names your bucket explicitly

Why findmnt and not gcloud storage ls? Because findmnt just reads your own mount table — no permissions, no network — and because the obvious-looking alternative is blocked on purpose:

$ gcloud storage ls
ERROR: (gcloud.storage.ls) HTTPError 403: Caller does not have
storage.buckets.list access to the Google Cloud project.

A bare gcloud storage ls means "list every bucket in the project", not "list mine". You cannot do that, by design — that is exactly what stops anyone enumerating your workspace (§7). Once you name a bucket you own, everything works normally.

If ~/gcs does not exist, stop and tell the lab admin rather than working around it. See §8.

Step 4 — Get your dataset in

Pick the method that matches where the data is coming from.

(a) Straight off the internet — curl or wget

mkdir -p ~/gcs/datasets
curl -fsSL https://storage.googleapis.com/download.tensorflow.org/example_images/flower_photos.tgz \
  -o ~/gcs/datasets/flower_photos.tgz
ls -lh ~/gcs/datasets/

That URL is real — a 218 MB public tarball — so you can run the block as it stands and see it work before pointing it at your own data.

Always check the ls afterwards. Those flags make curl silent in both directions: -s suppresses progress, and -f suppresses the error body — which is what you want, because without -f curl happily writes an HTML error page into your bucket and you discover it much later. The cost is that a wrong URL prints nothing at all, exits quietly, and leaves you with a missing or empty file; the failure then surfaces later, somewhere that looks unrelated.

(b) Hugging Face — and this one has a trap worth calling out:

# Point the HF cache at GCS FIRST. Its default is ~/.cache, on your 20 GB
# home disk, and a large model or dataset will fill it.
export HF_HOME=~/gcs/.cache/huggingface

hf download --repo-type dataset stanfordnlp/imdb \
  --local-dir ~/gcs/datasets/imdb

The command is hf, not huggingface-cli. This image ships huggingface_hub 1.x, in which the old name still exists but is a stub: it prints “huggingface-cli is deprecated and no longer works”, downloads nothing, and exits non-zero. Inside a notebook cell that is easy to scroll past, so you are left with an empty directory and no obvious reason why.

Put that export in ~/.bashrc so you cannot forget it.

(c) Kaggle — the kaggle CLI is preinstalled; you supply your own API token (~/.kaggle/kaggle.json, from your Kaggle account page):

kaggle datasets download -d some/dataset -p ~/gcs/datasets/ --unzip

(d) From another GCS bucket, or anything above a few GB — use gcloud storage, not the mount

gcloud storage rsync -r gs://cloud-samples-data/ai-platform/iris "gs://$MY_BUCKET/datasets/iris"

That source bucket is real and public too, and small, so the command is safe to run as a rehearsal before you aim it at a dataset that takes an hour.

This is the single biggest performance lever in this guide. gcloud storage transfers in parallel, server-to-server, and never stages the data on your pod. Copying a large dataset "through" ~/gcs makes your pod the bottleneck and can exhaust its local scratch space.

(e) From your laptop — small files: drag them into the JupyterLab file browser, then mv them into ~/gcs. Large files: run gcloud storage cp big.tar gs://hdlab-elideng-jupyter-<your-username>/ from your own machine instead — going through the browser and the pod is slow and fragile. (On your laptop you are you, not the pod, so $MY_BUCKET is not set there and you do have to type the name.)

Step 5 — Use the data from a notebook

First, the one-liner that gets your bucket name in Python — the notebook kernel is not your shell, so $MY_BUCKET from the terminal is not visible here:

import subprocess

MY_BUCKET = subprocess.check_output(
    ["findmnt", "-n", "-o", "SOURCE", "/home/jovyan/gcs"], text=True
).strip()
print("my bucket:", MY_BUCKET)          # -> hdlab-elideng-jupyter-elideng

Now, two ways to read the same object. Both work; they suit different jobs.

import pandas as pd

# Through the mount -- ordinary file paths. Best for browsing, small/medium files,
# and any library that insists on a real filesystem path.
df = pd.read_csv("/home/jovyan/gcs/datasets/iris.csv")

# Native gs:// URL via gcsfs -- no FUSE in the path. Faster for one big
# sequential read, and it works identically outside this hub.
df = pd.read_csv(f"gs://{MY_BUCKET}/datasets/iris.csv")

Parquet, which is what most real datasets arrive as:

df.to_parquet("/home/jovyan/gcs/datasets/iris.parquet")
df = pd.read_parquet(f"gs://{MY_BUCKET}/datasets/iris.parquet")

The SDK, for anything the filesystem view cannot express — resumable uploads, object metadata, listing with prefixes:

from google.cloud import storage
client = storage.Client()                      # no credentials argument needed
bucket = client.bucket(MY_BUCKET)              # from the findmnt snippet above
print(bucket.blob("datasets/iris.csv").download_as_text()[:200])

Preinstalled on every profile, so none of this needs a pip install: gcloud, gsutil, google-cloud-storage, gcsfs, huggingface_hub, kaggle, pandas, pyarrow.

Step 6 — Training: write checkpoints locally, then sync

Do not point a training loop's checkpoint directory straight at ~/gcs. Every save rewrites whole objects over the network and your step time will suffer. Write to local disk and push deliberately:

import os, torch
os.makedirs("/tmp/ckpt", exist_ok=True)

for epoch in range(epochs):
    train_one_epoch()
    torch.save(model.state_dict(), f"/tmp/ckpt/epoch{epoch}.pt")   # fast, local
    if epoch % 5 == 0:                                             # sync occasionally
        os.system("gcloud storage rsync -r /tmp/ckpt "
                  f"gs://{MY_BUCKET}/checkpoints/run-42")

Use /tmp or a subdirectory of ~ for the staging area — remembering the 20 GB home limit if you choose ~. And sync your final artifacts before you shut the server down.

4. Shared datasets (~/shared)

~/shared is a common bucket mounted read-only for everyone. If somebody has already pulled ImageNet or C4, look there before spending an hour and a lot of egress downloading it again.

ls ~/shared
cp ~/shared/some-dataset/file.parquet ~/gcs/work/     # copy out to work on it

touch ~/shared/anything
# touch: cannot touch '/home/jovyan/shared/anything': Read-only file system

That error is the mount working as designed, not a bug. To publish something into the shared bucket, ask the lab admin — it is deliberately not writable from a notebook, so that nobody can quietly modify a dataset other people's results depend on.

6. Seven things about ~/gcs that will surprise you

~/gcs looks like a directory, but it is a filesystem shim over object storage. Most of the time the illusion holds. Where it breaks:

  1. It is not POSIX. No hard links, no atomic directory rename, and a partial write rewrites the entire object.
  2. Do not put a git repo, a SQLite database, or a conda environment there. They rely on exactly the semantics above. They will be slow, and can corrupt. Those belong in ~.
  3. Empty directories barely exist. mkdir ~/gcs/foo can silently vanish until something is written inside it. Object storage has no directories, only key prefixes.
  4. ls on a huge prefix is slow. It is a paginated API call, not a directory read. Organise into subdirectories rather than dumping 100k objects at one level.
  5. Many-small-files is the worst case. Per-object overhead dominates. Pack into shards — tar, parquet, webdataset — before writing.
  6. There is no quota and no automatic cleanup. Nothing stops you filling the bucket and running up the bill. Delete what you are finished with: gcloud storage rm -r "gs://$MY_BUCKET/old-run/"
  7. Very large single writes stage on local scratch. A multi-hundred-GB write through the mount can hit the sidecar's 100 GB scratch limit. Above a few GB, use gcloud storage (§Step 4d). For reference, a 512 MB write through the mount was measured at 132 MB/s.

7. Privacy and isolation — what is actually guaranteed

Your workspace is a separate bucket, not a folder inside a shared one, and your notebook runs as its own cloud identity whose only storage permission is that one bucket. Isolation is a property of the resource boundary, not of a rule someone might mis-edit.

Verified live on the running cluster, from inside a notebook:

# Your own workspace, named explicitly -- ALLOWED
$ gcloud storage ls "gs://$MY_BUCKET/"
gs://hdlab-elideng-jupyter-elideng/datasets/

# Another user's workspace -- DENIED
$ gcloud storage ls gs://hdlab-elideng-jupyter-someone-else/
ERROR: ... does not have permission ... Permission 'storage.objects.list' denied

# You cannot even enumerate what buckets exist -- DENIED
$ gcloud storage ls
ERROR: ... Permission 'storage.buckets.list' denied on resource

Read those three together, because the difference matters in practice: you can do anything you like inside a bucket you name, and nothing at all across buckets. That third command is the one people trip over — it looks like "list my stuff" but actually means "list the project's stuff", so it fails for everyone here, permanently and on purpose. That is also why §3 has you get your bucket name from findmnt rather than by listing.

Two consequences worth internalising:

  • Nothing you put in ~/gcs is visible to other hub users. Not the contents, not even the file names.
  • Nobody else can accidentally delete your data, and you cannot accidentally delete theirs.

Two honest caveats, so you can calibrate:

  • This is isolation between hub users. Project administrators and anyone with project-level Storage permissions can still see your bucket. It is not a secrets store, and it is not for anything requiring special handling.
  • You share a node with other notebooks. Isolation is about storage, not about compute side channels.

8. Troubleshooting

What you seeWhat it means / what to do
Spawn fails: "Could not prepare your GCS workspace" Provisioning failed and the hub refused to start a notebook without a workspace — by design. The message names the step. Report it; there is nothing to fix from your side.
~/gcs is missing entirely but the notebook started fine A configuration regression, not a you problem. Do not work around it by saving into ~ — you will fill the 20 GB disk. Tell the lab admin and quote this: "pod has no gcs-workspace volume."
Server never starts; stuck on "Your server is starting up" First logins are slow (bucket + IAM). GPU profiles also wait for capacity and possibly an image pull. Give it a few minutes; if it times out, try the CPU profile to isolate whether it is capacity or configuration.
gcloud or SDK calls hang, then time out The pod cannot reach the metadata server to get a token. Infrastructure — report it.
~/gcs looks empty but you know the bucket has objects Check which bucket you are actually looking at (findmnt -n -o SOURCE ~/gcs), then list it directly with gcloud storage ls "gs://$MY_BUCKET/". Also remember empty "directories" may not appear (§6.3).
403 ... Permission 'storage.buckets.list' denied from gcloud storage ls Working as intended — you are not meant to be able to list the project's buckets. Name your own bucket instead: export MY_BUCKET=$(findmnt -n -o SOURCE ~/gcs) then gcloud storage ls "gs://$MY_BUCKET/". See §3 and §7.
ModuleNotFoundError: pandas You are on an image older than v2. Fully stop your server (§10) and start it again so it picks up the current image.
Read-only file system writing to ~/shared Working as intended. Copy out to ~/gcs to modify (§4).
JupyterLab cannot save; "no space left on device" Your 20 GB home disk is full. du -sh ~/* | sort -h, then move the large things into ~/gcs. Usual culprits: an unredirected HF cache, pip caches, checkpoints written to ~.

9. Recent change worth knowing about

Shipped 27 Aug 2026, alongside these workspaces: a long-standing bug meant the 8-GPU TCPXO profile silently had no persistent home directory. Notebooks opened normally, so it was easy to miss, but anything saved in ~ on that profile was lost when the pod was replaced. It is fixed, and there is now a test that fails if any profile regresses it.

If you used the 8-GPU profile before that date and wondered where a file went — that is why, and unfortunately it is not recoverable. Anything you had put in ~/gcs was never affected.

10. Shutting down (please do)

File → Hub Control Panel → Stop My Server. Closing the browser tab does not stop it.

This matters most on the GPU profiles: an idle 8-GPU notebook holds an entire scarce A3-Mega node that a colleague may be queuing for. Nothing in ~ or ~/gcs is lost by stopping — that is the whole point of both.
